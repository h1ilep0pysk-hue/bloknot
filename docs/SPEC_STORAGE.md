# SPEC_STORAGE — SQLite, сериализация, автосохранение

> Обязательная спецификация. Отвечает на вопросы: где лежат данные, что именно записывается, когда, как восстанавливается и что делать, если файл повреждён.

## 1. Расположение и создание базы

- Файл: `data/bloknot.sqlite3` рядом с `main.py`. Папка `data/` создаётся автоматически, если её нет; в `.gitignore` (данные пользователя не в репозитории).
- Первое подключение: `sqlite3.connect(...)`, затем создать таблицу (п. 2). Открытие и создание — в `storage/db.py`, никаких прямых `sqlite3` в других слоях.
- Почему SQLite и одна таблица: приложение локальное, однопользовательское; полноценная СУБД не нужна, а файл переносной — можно закинуть на флешку вместе с кодом.

## 2. Схема БД

```sql
CREATE TABLE IF NOT EXISTS projects (
    id           TEXT PRIMARY KEY,
    name         TEXT NOT NULL,
    idea_summary TEXT NOT NULL DEFAULT '',
    description  TEXT NOT NULL DEFAULT '',
    schema_json  TEXT NOT NULL DEFAULT '{"version": 2, "nodes": [], "edges": []}',
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL
);
```

| Колонка | Пояснение |
|---|---|
| `id` | Первичный ключ, uuid4.hex из модели. TEXT, не INTEGER: идентификаторы уже строковые и не зависят от автонумерации |
| `name` | Название проекта, обязательное |
| `idea_summary` | Краткая идея (уже обрезанная сервисом до 280 символов) |
| `description` | Подробный текст |
| `schema_json` | Вся схема одним JSON: узлы + связи + runtime-строки значений |
| `created_at` / `updated_at` | ISO 8601 UTC строкой |

PRAGMA при каждом открытии: `journal_mode=WAL` (не блокирует чтение при записи), `synchronous=NORMAL`.

## 3. Структура `schema_json`

```json
{
  "version": 2,
  "nodes": [
    {
      "id": "a1f0c2...",
      "type": "number",
      "title": "Число",
      "x": 120.0,
      "y": 90.0,
      "params": {"value": 2.0}
    }
  ],
  "edges": [
    {
      "id": "e01ab...",
      "from_node": "a1f0c2...",
      "from_port": 0,
      "to_node": "b2c4d1...",
      "to_port": 0
    }
  ],
  "runtime": {
    "a1f0c2...": {"outputs": {"out": "2.0"}, "error": null}
  }
}
```

| Поле | Пояснение |
|---|---|
| `version` | Версия формата (см. п. 5). При чтении число сверяется; неисторию версия → миграция |
| `nodes[].type` | Ключ реестра. Неизвестный ключ не выбрасывает узел: узел сохраняется, загружается как `unknown` (SPEC_CORE, п. 9) |
| `nodes[].x/y` | float; координаты угла узла |
| `nodes[].params` | Значения виджетов: spin → число, line/combo → строка, text/code → строка. Инлайн-виджеты и панель пишут в один и тот же `params` |
| `edges[]` | Связи. Выходов у одного узла может нес-ко, вход один — это обеспечивается валидацией при создании |
| `runtime` | **Только repr-строки** (`repr(value)`, обрезанные до 1000 символов) последних значений и ошибки. Зачем: после перезапуска граф открывается с уже показанными числами, как на скрине. Это строка-декорация: она никогда не исполняется обратно в объекты — живой пересчёт происходит при первой правке |

Правила:

- Живые объекты (numpy-массивы, большие списки) в JSON не попадают никогда — только repr.
- `runtime` — ошибка узла тоже строка (`"error": "деление на ноль"`), чтобы показать её до первого пересчёта.

## 4. Запись (репозиторий)

- Одна операция: `INSERT ... ON CONFLICT(id) DO UPDATE` — создаёт или переписывает строку целиком. Без diff-логики: проект маленький (десятки КБ), полная перезапись проще и надёжнее частичных обновлений.
- Каждая запись обновляет `updated_at`.
- Транзакция на каждую запись; коммит сразу (WAL делает это дешёвым).
- Репозиторий даёт только: `get_all()`, `get(project_id)`, `create(...name, idea_summary, description)`, `update(...поля)`, `delete(project_id)`. Никакой доменной логики внутри — он про SQL, не про смысл.

## 5. Миграции формата схемы

- При чтении: если `version` отсутствует или `< 2` → привести к текущей (для 1→2: добавить `"runtime": {}`), записать мигрированную версию обратно при первом сохранении.
- Будущие версии: движок миграций не нужен, достаточно цепочки `if` в `schema_service.deserialize`. Узлы с неизвестными типами → `unknown`-узлы (SPEC_CORE, п. 9), лишние параметры в `params` — остаются (безвредно), недостающие — добираются из `NodeSpec.default`.

## 6. Автосохранение (кто, когда, как)

| Событие | Что меняется | Действие |
|---|---|---|
| Правка идеи/описания/названия | текстовые поля | mark dirty → debounce **500 мс** → запись |
| Правка параметра узла (inline или панель) | `params` + пересчёт | mark dirty → debounce 500 мс → запись |
| Создание/удаление узла или связи | структура графа | mark dirty → debounce 500 мс → запись |
| Перемещение узла | `x/y` | записывается однократно при отпускании мыши |
| Пересчёт значений | `runtime` repr | записывается **вместе** со следующей структурной/текстовой правкой; отдельного таймера нет (runtime — это вид, не документ) |
| Закрытие окна | всё | финальная немедленная запись без debounce |

Механика debounce (в `app.py` или `main_window.py`, не в движке): один `QTimer` (singleShot, 500 мс); любое изменение перезапускает его; по срабатывании — `project_service.flush()` → `project_repository.update(...)`. Состояние-флаг «есть несохранённое» снимается после записи.

## 7. Чтение и восстановление

1. `project_repository.get(id)` → строка `schema_json`.
2. `schema_service.deserialize(str)` → `SchemaGraph`: нормализация типов (`x` → float и т.п.), миграция версии, чистка.
3. Чистка (`core/validation.py`, п. 10): связи на несуществующие узлы/порты — удалить; дубли id — оставить первый.
4. `flow_service.init_runtime(schema)` → `NodeRuntime` заполнен repr-значениями из JSON, `dirty=True`.
5. UI рисует граф; чипы показывают восстановленные значения приглушённо (пометка «восстановлено» — until первый пересчёт).
6. Битый JSON / отсутствует ключ → схема пустая + тост «Схема не прочитана и была сброшена» — приложение не падает.

## 8. Ошибки хранилища

| Ситуация | Поведение |
|---|---|
| База не открывается (файл занят/повреждён) | Диалог «База данных недоступна» + работа в памяти с тостом «Не сохраняется» — можно хотя бы посмотреть и скопировать |
| Ошибка записи (диск переполнен) | Тост «Не удалось сохранить», повтор при следующем debounce; приложение живёт |
| Дубли проектов после слияния баз | Не проблема: id uuid, разные записи мирно живут списком |

## 9. Удаление проекта

- Из сайдбара по ПКМ → подтверждение (диалог да/нет) → `DELETE` → выбрать соседний проект; если пусто — пустое состояние (SPEC_UI, п. 8).
- Удаление физическое, без корзины: файл маленький, а «корзина» — усложнение v1.

# Bloknot — архитектура (главный документ)

> Блокнот проектировщика приложений: сверху — идея в 1–2 предложениях, ниже — подробное описание, на второй вкладке — **исполняемая** схема из блоков (dataflow): узлы реально вычисляются, живые значения видны прямо внутри узлов — как в Ryven (референс-скриншот с узлами Determinant / Inverse / eval / result).

## 1. Суть продукта

### 1.1 Три контура проектирования

1. **Текст.** Краткая идея (1–2 предложения, ≤280 символов) + подробное описание (как работает, какая архитектура, что откуда берёт). Зачем: если идея не формулируется в 280 символах — она ещё не сформулирована.
2. **Схема-план (проектные блоки).** Блоки вида «Сайт / URL → Парс HTML → Извлечь данные → Использовать у себя». Зачем: показать человеческим языком логику будущей программы, чтобы её можно было понять, обсудить или отдать ИИ (экспорт Markdown + Mermaid).
3. **Живой dataflow (исполняемые блоки).** Блоки вида «Число → Оператор(**) → eval → Результат» реально выполняются: значения бегут по связям, и результат виден прямо в телах узлов. Зачем: прототип логики собирается руками и мгновенно проверяется — до написания настоящего кода.

Контуры 2 и 3 живут **на одной канве** и соединяются: проектный блок можно вставить в исполняемую цепочку — он отдаёт строку-описание своего шага, и пересчёт через него не прерывается.

### 1.2 Ключевой принцип

**Узел = функция, связь = значение.**

- Узел — это спецификация (`NodeSpec`) + её экземпляр (`Node`): у блока есть входные порты, выходные порты и функция `fn`, которая из значений входов и параметров вычисляет значения выходов.
- Связь не «проводит сигнал от кнопки к кнопке», как в муляжах, — она переносит **конкретное значение** (число, текст, список, матрицу) с выхода одного узла на вход другого.
- Когда меняются параметр или вход узла, пересчитывается только нижестоящая часть графа (подграф), а результат сразу отображается в телах узлов — как на скрине Ryven: `Determinant → 6.0`, `eval → inp[0][0]`, `result → [37.+0.j …]`.

### 1.3 Чем это отличается от «просто рисованной схемы»

В нарисованном прототипе блоки — картинки: соединил линии и «как будто работает». Здесь соединение ветки **разрешено или запрещено движком** (один вход — одна связь, циклы запрещены, несовместимый тип — ошибка узла), а каждое значение — вычислено. Схема не может «врать»: если она соединена — она считается; если считать нельзя — узел честно показывает ошибку.

## 2. Пользовательские сценарии (как должно работать)

**С1. Записать идею.** Открыл приложение → «+ Новый проект» → ввёл название, 1–2 предложения идеи, развёрнутое описание → всё само сохранилось (debounce 500 мс) → закрыл — открыл: на месте.

**С2. Спланировать парсинг.** Вкладка «Схема» → перетащил «Сайт / URL», «Парс HTML», «Извлечь данные», «Использовать у себя» → соединил выходы со входами → вписал url и селектор в inline-поле узла. Это план; значения проектных блоков — описательные строки.

**С3. Проверить логику на живых данных.** Там же перетащил «Число»(2), «Оператор»(op=**), «Python-выражение»(expr=`in0[0][0]`), «Результат» → соединил → в теле «Оператора» сразу видно `8`, в «Результате» — результат. Изменил spin числа с 2 на 3 → оба значения пересчитались сами (Live-режим, debounce 200 мс).

**С4. Вернуться завтра.** Открыл проект — граф восстановлен: позиции узлов, связи, параметры и последние значения (результаты хранятся как repr-строки для восстановления вида; при первой правке пересчитывается живыми объектами).

**С5. Отдать проект наружу.** Кнопка «Экспорт Markdown» → файл: название, идея, описание, шаги схемы (топологический порядок) + Mermaid-диаграмма. Так проект можно показать человеку или скормить другому ИИ.

## 3. Карта системы (слои)

```
┌────────────────────────────────────────────────────────┐
│ UI (PySide6)                                           │
│  окно, сайдбар проектов, вкладки «Идея» / «Схема»,     │
│  канва: узлы (порты, inline-виджеты, чипы значений),   │
│  пунктирные связи, панель параметров, тумблер Live     │
│  — только отображение, события и таймеры debounce      │
├────────────────────────────────────────────────────────┤
│ Services                                               │
│  project_service — CRUD проектов                       │
│  schema_service  — (де)сериализация графа, миграции    │
│  flow_service    — исполняющий движок (dataflow)       │
│  export_service  — Markdown + Mermaid                  │
├────────────────────────────────────────────────────────┤
│ Core (домен)                                           │
│  Project, SchemaGraph, Node, Edge, NodeRuntime         │
│  PortSpec, ParamSpec, NodeSpec, реестр блоков          │
│  правила целостности графа                             │
├────────────────────────────────────────────────────────┤
│ Storage                                                │
│  SQLite (sqlite3 stdlib) + project_repository          │
│  — единственное место с SQL                            │
└────────────────────────────────────────────────────────┘
```

Правила:

- Зависимости идут сверху вниз: `UI → Services → Core → Storage`.
- `core/`, `services/`, `storage/` **не импортируют PySide6**. Почему: движок и хранение тестируются без интерфейса, домен не «протекает» в графику.
- Движок не использует сигналы Qt: UI подписывается колбэком `on_values(changed_node_ids)` — движок остаётся чистым.
- Исполнение синхронное, однопоточное. Debounce-таймеры держит UI, движок — только логика.

## 4. Сквозной пример: что происходит при изменении числа

Чтобы стало ясно, как слои работают вместе:

1. Пользователь крутит spin в inline-виджете узла «Число» на канве (UI, `node_item`).
2. UI вызывает `project_service.set_param(node_id, "value", 3)` → модель `Node.params` обновлена.
3. `project_service` уведомляет: структура/параметры изменились → `flow_service.invalidate(node_id)` (узел помечен dirty) и `schema_service` ставит задачу автосохранения.
4. Через 200 мсdebounce-таймер UI вызывает `flow_service.evaluate_pending()`.
5. Движок: обход от изменённого узла вниз по связям → подграф → топосорт → для каждого узла: собрать входы (None, если связи нет), привести к типам портов, вызвать `fn` → значения выходов.
6. Ошибка в узле? → `NodeRuntime.error = текст`, вниз передаётся ошибка (нижестоящие показывают «—»). Приложение не падает.
7. Движок вызывает `on_values(changed_ids)` → UI перерисовывает чипы значений и полосы состояний этих узлов.
8. Через 500 мс после последнего изменения — автосохранение: SQLite `UPDATE`, схема включает repr-строки свежих значений.

## 5. Глоссарий (термины, использованные в спецификациях)

| Термин | Значение |
|---|---|
| Проект | Запись в БД: название + идея + описание + схема |
| Схема / граф | `SchemaGraph`: узлы + связи конкретного проекта |
| Узел | Экземпляр блока на канве (`Node`), имеет тип из реестра |
| Блок (spec) | Тип узла в реестре: `NodeSpec` — описание, коим рисуется и вычисляется |
| Порт | Точка узла: вход (слева) или выход (справа); у порта есть имя, индекс и тип |
| Связь (ребро) | `Edge`: выход одного узла → вход другого; переносит значение |
| Чип значения | Инлайновое отображение значения порта внутри узла (моноширинный текст) |
| Inline-виджет | Редактор параметра прямо в теле узла (spin, combo, code-поле) |
| Исполняемый блок | Block с `runnable=True` и функцией `fn` — участвует в dataflow |
| Проектный блок | Блок планирования (`runnable=False`): отдаёт строку-описание шага |
| Runtime | Живое состояние узла: последние значения выходов + ошибка (`NodeRuntime`) |
| Dirty | Узел, чьё значение устарело и требует пересчёта |
| Подграф пересчёта | Узел + все нижестоящие по связям узлы, которых коснулось изменение |
| Топосорт | Топологическая сортировка — правильный порядок вычисления графа |
| Debounce | «Соединённый» таймер: пересчёт/запись запускается паузой после последнего события |
| Live-режим | Автопересчёт при любом изменении (вкл. по умолчанию); иначе — по кнопке «▶» |
| Песочница eval | Исполнение выражения из узла `eval` с урезанными builtins (import невозможен) |
| repr-строка | Текстовый вид значения (`repr(v)`) для сохранения в JSON и восстановления вида |

## 7. Ключевые инварианты системы

Нарушение любого из них = брак:

1. Связь всегда `выход → вход`; соединить узел с самим собой нельзя.
2. У входа максимум одна связь: новая связь заменяет старую.
3. Циклы в графе запрещены: попытка соединения, создающая цикл, отклоняется; если цикл появился при загрузке — узлы цикла получают ошибку «цикл в схеме» и не вычисляются.
4. `fn` узла — чистая функция: без Qt, без глобального состояния, без побочных эффектов; исключение внутри `fn` — это ошибка узла, а не краш приложения.
5. Вход без связи = `None`; приведение типов делает движок до вызова `fn`.
6. В БД никогда не хранятся живые объекты значений — только repr-строки в блоке `runtime`.
7. Значения вычисляет только `flow_service` (никаких «зашитых» значений для вида).
8. Все цвета — только константами из `ui/theme.py`; ни один виджет не хардкодит цвет.
9. `core/`, `services/`, `storage/` не импортируют PySide6.
10. Приложение однопоточное: никаких QThread; тяжёлые вычисления — забота фазы 2.

## 8. Частые ошибки реализации (на что смотреть при приёмке)

- **Муляж-канва**: узлы показывают «зашитые» красивые значения вместо вычисленных. Лечится инвариантом 7.
- **Пересчёт всего графа на каждый чих** вместо подграфа — тормозит и мигает чипами.
- **Запись в БД на каждый апдейт** (каждый кадр спина) вместо debounce 500 мс.
- **Хардкод цветов** в виджетах — ломает тему и минимализм.
- **Исключение в узле роняет приложение** — ошибка узла должна стать его состоянием.
- **Забытые inline-виджеты**: параметры существуют только в панели — а обязаны быть и в теле узла, где помечены inline.
- **QGraphicsProxyWidget перехватывает колесо** — зум канвы над inline-виджетом умирает; нужен eventFilter (см. SPEC_UI).
- **Живые объекты в JSON** (numpy-массивы и т.п.) — в JSON уходит только repr.
- **Светлые/яркие цвета** — вся палитра тёмно-серая, см. SPEC_UI.

## 9. Фазы

1. **v1 (текущий скоуп)** — блокнот + вкладки; канва с палитрой, inline-виджетами и чипами значений; исполняемый dataflow (12 блоков), песочница eval, Live-режим, автосохранение, экспорт Markdown.
2. **v2 (дальше)** — проектные блоки становятся исполняемыми (Сайт/URL → запрос, Парс HTML → BeautifulSoup, опциональные зависимости); exec-рёбра в стиле n8n (отдельный порядок выполнения от данных); тяжёлые вычисления в потоке.
3. **v3** — шаблоны схем; генератор ТЗ «описание + схема → промт для Claude».

## 10. Краткий определённый стек

- Python 3.11+, PySide6 ≥ 6.6. `requirements.txt`: `pyside6`; numpy — необязательная зависимость (матричные блоки деградируют с подсказкой, см. SPEC_FLOW).
- Хранилище: один файл `data/bloknot.sqlite3`, WAL.
- Запуск: `python main.py` (Windows), окно 1280×800, минимальное 960×640.
